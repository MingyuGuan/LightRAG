## Query Quality Evaluation:

Ran query quality evaluation on both the sample dickens dataset and the agriculture dataset. 
To generate the agriculture dataset, use the [reproduce](../../reproduce) folder.
1. Download the agriculture dataset from [HuggingFace](https://huggingface.co/datasets/TommyChien/UltraDomain) ( this link can be found on the main ReadMe too). It will be a .jsonl file with each element of the form: input question, answer and the context from which the answer is derived. 
2. Run Step_0.py script in reproduce directory to create a .json file of unique contexts extracted from the .jsonl script. 
3. The Step_1* scritps are used to insert the json data into RAG. Can be skipped if you write your own script for insertion. Although do note that this script iterates over the individual json contexts and inserts it as separate documents which might be helpful since the local vllm run setup tends to result in timeout errors for huge documents. 
4. The Step_2.py generates questions for the dataset: 5 users and 5 tasks, resulting in a net of 125 questions.
5. The Step_3* scirpt is used to run the RAG for the questions. Can be skipped if you write your own script for insertion. 


### Helper scripts:
In the [eval directory](../eval)

* [query_runtime_evaluator.py](./query_runtime_evaluator.py) can be used to both insert document into rags and to query rags given an input json file. It has a bunch of command line arguments that can be used to customize the run. 
* [models_comparator.py](./models_comparator.py) Compares the answer generated by 2 models (i.e the output of the query_runtime_evaluator.py) using structuring specified in the LightRAG paper. The LLM’s evaluation is stored—along with the original answers—in a new JSON output file whose name reflects the two models being compared.
* [format_comparison_results.py](./format_comparison_results.py) This script processes the evaluation JSON file produced by the models_comparator.py.
It looks for "raw" fields containing the model’s evaluation in string form, attempts to parse them into structured JSON, and replaces them with a "Comparison" object.
The cleaned and structured results are then saved to a new JSON file with `_cleaned` appended to the original filename. The cleaing is separated from the models_comparator step since it was noticed that the llm sometimes returned a string instead of the requested json and causing errors to happen during conversion. 
Instead the result is stored in a file and then parsed to get the json out of it. The result returned by the llm for the comparison comes in various forms most of which gets parsed into json object by this script. There were cases where the raw result was a combination of a string and json object. Manual updates were made in such cases.
* [comparison_result_cvs_conversion.py](./comparison_result_cvs_conversion.py) Takes the cleaned model evaluation JSON file and converts it into two CSV outputs: 

    * **Detailed results CSV** – Flattens the nested JSON into rows containing Role, task, and question, the two model answers, The winner and explanation for each evaluation criterion 

    * **Summary CSV** – Counts how many times each model (Lightrag vs. Graphloom) or a tie won in each criterion, and includes a total count per category.





### Notes: 
* During rag insertion, there might be cases where the run fails due to a transient timeout error. The kv_store_llm_response_cache.json can be reused since the code checks if the entry exists before insertion. This is not ture for the other json files since its an append. My approach was to make a copy of the running directory for safekeeping, delete the scripts other than the log(gets appended and is useful to get the entire history of runs) and the respone_cache and then re-kick off the run. 
```
find . -type f ! -name 'graphloom.log' ! -name 'kv_store_llm_response_cache.json' -delete
```
* While cleaning up the repo, I have reordered the scritps into different directories so update the file paths wherever necessary. 

* If you have multiple LightRag repo cloned to maybe test out various stages of the project, make sure that the code being executed is from the relevant version. 
I had 2 lightrag repos and one of them was getting picked up despite executing in the relevant directory( i.e the import lightrag was picking up the module from the other directory. ). I used export PYTHONPATH=<path> to redirect to the correct directory

* During time out errors I increased the number of GPU devices that runs the llm for generating the results to the max number of 7( a total of 8 were available, but was needed to run the embedding model)
